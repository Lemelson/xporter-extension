# Разбор удалений XPorter 1.5.0 и исправления 1.5.1

Дата анализа: 26 июля 2026
Источник: `/Users/lemelson/Downloads/UninstallsXPorter (8).xlsx`, строки 101–111

## Короткий вывод

Главная проблема 1.5.0 была не в общей скорости XPorter, а в восстановлении после изменений внутренних запросов X. Особенно ломалась включённая по умолчанию вкладка Replies: экспорт мог долго показывать паузы, повторять уже исчерпанный цикл восстановления и закончиться с нулём строк. При этом Posts-only тоже мог получить `STALE_QUERY_ID`, поэтому простого отключения Replies было недостаточно.

В 1.5.1 исправлен сам протокол запроса: XPorter хранит принятые X query ID и boolean feature flags как одну атомарную, безопасно очищенную форму запроса; для Replies локально генерирует обязательный `x-client-transaction-id`; обновляет transaction challenge ровно один раз и повторяет тот же подтверждённый запрос; после исчерпания вариантов останавливается без минут ложных пауз.

## Что показало сравнение с конкурентами

Были проверены установленные в Helium расширения Twitter Export Followers, XExporter, Rovver, TwExport, TwExtract и Tweet Export Pro.

- XExporter сохраняет форму реального нативного GraphQL-запроса целиком. Полезная идея — query ID нельзя отделять от соответствующих feature flags. Небезопасную часть решения (полные headers, cookies/storage и backend) XPorter не копирует.
- TwExport добавляет динамический `x-client-transaction-id` для Replies. В живом тесте он собрал 113 строк там, где XPorter 1.5.0 оставался на 0. Это подтвердило недостающий элемент протокола.
- Rovver в основном пассивно собирает уже показанное при прокрутке. Это снижает число дополнительных запросов, но не заменяет полный экспорт произвольного профиля и ограничено тем, что пользователь реально проскроллил.

## Подтверждённые причины

1. Любой HTTP 400/404 считался stale query ID, но persisted endpoint cache оставался и возвращался после перезапуска MV3 worker.
2. Успешное обнаружение endpoint не требовало, чтобы была найдена именно активная операция Replies.
3. Query ID из живого запроса соединялся со статическими feature flags другой версии клиента X.
4. Для `UserTweetsAndReplies` отсутствовал обязательный динамический transaction header.
5. Внутренний stale-recovery уже перебирал все кандидаты, после чего внешний rate limiter повторял весь цикл ещё до пяти раз с паузами 10/20/30/40/50 секунд.
6. После обновления transaction challenge тот же принятый native template не пробовался повторно.
7. Ошибка инициализации transaction context могла повторять 15–30-секундную загрузку для каждого query ID.
8. HTTP 200 с GraphQL `errors` и без timeline превращался в «успешный» экспорт 0 строк.
9. Resume восстанавливал rate-limit state, затем заново запрашивал пользователя и обнулял счётчики; popup временно показывал 0.
10. Resume после Stop/error ошибочно добавлял ещё 100 строк и менял исходный лимит.
11. Частичный Posts-only экспорт терял предупреждение после Stop/Resume и не отличался от полного в истории.

## Что изменено в 1.5.1

- Атомарный privacy-safe native request template: только операция, query ID и плоские boolean `features`/`fieldToggles`.
- Шаблон принимается только после успешного нативного GET и хранится 30 минут; variables, URL, headers, cookies, username, user ID и cursor не сохраняются.
- Локальная генерация `x-client-transaction-id` для Replies с bundled MIT notice.
- Один bounded refresh transaction challenge с повтором того же кандидата.
- Ошибка инициализации transaction context временно кэшируется, чтобы не умножать тайм-аут на число query ID.
- Persisted stale cache удаляется; discovery знает, какие операции действительно найдены.
- Полностью исчерпанный stale-cycle больше не повторяется внешним rate limiter.
- Replies стал opt-in по умолчанию для новых установок; сохранённый выбор существующих пользователей не перезаписывается.
- Если Replies снова изменится и собрано 0 строк, пользователь видит отдельный экран: Retry Replies или явное Continue with Posts only.
- Posts-only fallback не меняет глобальную настройку, сохраняет лимит и маркируется в статусе и истории.
- Resume после Stop/error сохраняет исходный лимит, rate-limit counters, собранное количество и partial marker.
- HTTP 200 без пригодной timeline теперь запускает bounded stale-recovery, а не зелёный 0-row success.
- Все новые состояния переведены на 14 языков; privacy policy уточняет чтение публичного X CDN asset без cookies/auth и без исполнения remote code.

## Проверка

- До исправления: один и тот же живой Replies-экспорт `FWPlayboy`, limit 100, Turbo — 0 строк и повторяющиеся паузы «API changed».
- После основного исправления: 100/100.
- Финальный авторизованный smoke именно XPorter 1.5.1 в Helium: 42 строки примерно через 6 секунд, завершение 100/100 примерно за 21 секунду.
- Отдельный Chromium smoke: popup, service worker, content scripts, 14 локалей, dark/light, Replies fallback и partial-history.
- Детерминированные suites: static contracts, extension core, rate limit и feed capture.

Ограничение остаётся фундаментальным: X может снова изменить внутренний API. Разница 1.5.1 в том, что XPorter теперь повторно использует принятую X форму запроса, обновляет transaction challenge ограниченно и останавливается честно, а не имитирует бесконечную работу.
